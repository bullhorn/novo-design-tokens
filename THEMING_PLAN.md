# Reliable Theming: Implementation Plan

## Problem Statement

Today you can't reliably swap a theme at the root level and have everything respond. Some components use CSS variables (responsive), some use SCSS variables (baked at compile time), and some hardcode values entirely.

## Current State Assessment

### By the Numbers

| Strategy | Component files | Theme-responsive? |
|----------|----------------|-------------------|
| CSS variables `var(--*)` | 52 / 135 (38%) | Yes |
| SCSS variables `$color-*` | ~60 files | No |
| Hardcoded hex/rgba | 231+ instances | No |

### Token Layer Gaps

- **4 tokens** have dark variants (`theme.background.*`)
- **450+ tokens** are static regardless of theme
- `css/variables-dark.css` only contains 4 overrides
- Dark theme in novo-elements is hand-maintained in `styles/themes/dark.scss`, disconnected from the token system

### Why SCSS Variables Don't Work for Theming

SCSS variables resolve at compile time. `$color-ocean` becomes `#4a89dc` in the CSS output — there's no runtime hook to swap it. Additionally, SCSS functions like `darken($light, 10%)` can't operate on CSS variables.

**Verdict:** CSS custom properties are required for any value that changes between themes. SCSS remains useful for static utilities (mixins, loops, maps) and as the build-time source that assigns CSS variables.

## Architecture: Three-Layer Token System

```
┌─────────────────────────────────────────────────────┐
│  Layer 1: PRIMITIVES (novo-design-tokens)           │
│  Raw palette values, generated variants             │
│  color.ocean = #4a89dc                              │
│  color.ocean.shade = #3b6db0                        │
│  Static across all themes                           │
└─────────────────────────────┬───────────────────────┘
                              │ referenced by
┌─────────────────────────────▼───────────────────────┐
│  Layer 2: SEMANTIC TOKENS (novo-design-tokens)      │
│  Theme-aware aliases (value + darkValue):           │
│    surface.primary    = white / midnight            │
│    text.primary       = dark / light                │
│    interactive.base   = ocean / aqua                │
│    border.default     = light / onyx                │
│  Output: themed CSS variable sets                   │
└─────────────────────────────┬───────────────────────┘
                              │ consumed via var(--)
┌─────────────────────────────▼───────────────────────┐
│  Layer 3: COMPONENT TOKENS (novo-design-tokens)     │
│  Component-specific mappings:                       │
│    button.primary.bg = {interactive.base}           │
│    card.background   = {surface.primary}            │
│    input.border      = {border.default}             │
└─────────────────────────────────────────────────────┘
```

### Semantic Token Categories

| Category | Purpose | Example tokens |
|----------|---------|----------------|
| `surface` | Backgrounds at different elevations | primary, secondary, elevated, muted, inverse |
| `text` | Text/foreground colors | primary, secondary, disabled, inverse, link |
| `interactive` | Actionable element colors | base, hover, active, focus, disabled |
| `border` | Border/divider colors | default, subtle, strong, focus |
| `feedback` | Status communication | success, warning, error, info (+ text variants) |
| `overlay` | Modals, popovers, backdrops | background, scrim |

Each semantic token has a `value` (light) and `darkValue` (dark). ~40-60 tokens total.

## What a "New Style" Theme Looks Like

A theme is a CSS file generated by the token build that sets semantic variables under a selector:

```css
/* Default (light) — applied at :root */
:root {
  --surface-primary: #ffffff;
  --surface-secondary: #f7f7f7;
  --surface-muted: #f4f4f4;
  --text-primary: #3d464d;
  --text-secondary: #4f5361;
  --interactive-base: #4a89dc;
  --interactive-hover: #6ea0e3;
  --border-default: #dbdbdb;
  --feedback-success: #8cc152;
  /* ... */
}

/* Dark theme — applied via data attribute */
[data-theme="dark"] {
  --surface-primary: #1a242f;
  --surface-secondary: #161f27;
  --surface-muted: #4f5361;
  --text-primary: #dbdbdb;
  --text-secondary: #bebebe;
  --interactive-base: #3bafda;
  --interactive-hover: #62bfe1;
  --border-default: #526980;
  --feedback-success: #5fc9af;
  /* ... */
}
```

Creating a new theme = adding a new value set in `src/tokens/theme/`. The build produces the CSS. No component changes needed.

## Implementation in novo-elements

This is where the bulk of visible change happens. The work breaks into infrastructure changes and per-component migration.

### Infrastructure Changes

#### 1. Replace hand-maintained theme files

**Delete:**
- `styles/themes/light.scss` (hand-maintained CSS variable assignments)
- `styles/themes/dark.scss` (hand-maintained dark overrides)
- `styles/themes/light-test.scss` (incomplete experiment)

**Replace with import from tokens:**
```scss
// styles/themes/_index.scss
@import 'novo-design-tokens/css/themes';
```

The token build now owns the full theme definition. No hand-maintaining duplicate values.

#### 2. Update variables.scss

**Before (today):**
```scss
@import 'novo-design-tokens/scss';
$base-font-color: var(--color-dark);
$negative: $color-grapefruit;
$positive: $color-grass;
// ... 60+ local aliases
```

**After:**
```scss
@import 'novo-design-tokens/scss';

// Legacy aliases — kept only during migration, annotated for removal
// Components should use var(--feedback-error) not $negative
$negative: $color-grapefruit;
$positive: $color-grass;
```

Each alias gets a comment marking it as deprecated. As components migrate, these get deleted.

#### 3. Evolve ThemeDirective

**Before:**
```typescript
@Directive({ selector: '[novoTheme]' })
export class ThemeDirective implements OnChanges {
  @Input('novoTheme') theme: { [prop: string]: string };
  ngOnChanges() {
    Object.keys(this.theme).forEach((prop) => {
      this.el.nativeElement.style.setProperty(`--${prop}`, this.theme[prop]);
    });
  }
}
```

**After:**
```typescript
@Directive({ selector: '[novoTheme]' })
export class ThemeDirective implements OnChanges {
  @Input('novoTheme') theme: string | { [prop: string]: string };

  ngOnChanges() {
    if (typeof this.theme === 'string') {
      // Named theme: set data attribute, let CSS do the work
      this.el.nativeElement.setAttribute('data-theme', this.theme);
    } else {
      // Custom overrides: set individual properties (existing behavior)
      Object.keys(this.theme).forEach((prop) => {
        this.el.nativeElement.style.setProperty(`--${prop}`, this.theme[prop]);
      });
    }
  }
}
```

Now you can do `<div novoTheme="dark">` or `<div [novoTheme]="customObj">`.

#### 4. Update NovoTheme service

```typescript
@Injectable()
export class NovoTheme {
  private _themeName = 'light';

  use(config: { themeName: string }) {
    this._themeName = config.themeName;
    document.documentElement.setAttribute('data-theme', config.themeName);
    this.onThemeChange.emit(config.themeName);
  }
}
```

Theme switching becomes a one-liner: set `data-theme` on the root element.

### Component Migration Pattern

Each component migration follows this repeatable pattern:

#### Before (example: Checkbox.scss)
```scss
@import 'novo-design-tokens/scss';

.novo-checkbox {
  border: 1px solid $color-light;

  &.checked {
    background: $color-positive;
    border-color: darken($color-positive, 10%);
    color: #ffffff;
  }

  &.disabled {
    background: #d2d2d2;
    color: darken(#d2d2d2, 60%);
  }
}
```

#### After (same component)
```scss
.novo-checkbox {
  border: 1px solid var(--border-default);

  &.checked {
    background: var(--feedback-success);
    border-color: var(--color-grass-shade);
    color: var(--text-inverse);
  }

  &.disabled {
    background: var(--interactive-disabled);
    color: var(--text-disabled);
  }
}
```

#### What Changes in Each Migration

| Pattern | Replace with |
|---------|-------------|
| `$color-positive` | `var(--feedback-success)` |
| `$color-negative` / `$negative` | `var(--feedback-error)` |
| `$light`, `$color-light` | `var(--border-default)` or `var(--surface-muted)` depending on usage |
| `$dark`, `$color-dark` | `var(--text-primary)` |
| `$ocean` | `var(--interactive-base)` or `var(--text-link)` |
| `darken($x, n%)` | `var(--color-x-shade)` (pre-computed) |
| `lighten($x, n%)` | `var(--color-x-tint)` (pre-computed) |
| `#ffffff` / `#fff` (backgrounds) | `var(--surface-primary)` |
| `#ffffff` (text on dark bg) | `var(--text-inverse)` |
| `rgba(0,0,0,0.x)` (overlays) | `var(--overlay-backdrop)` |

### Component Migration Priority

Ordered by visibility × ease of migration:

| Priority | Component | Issue | Effort |
|----------|-----------|-------|--------|
| 1 | root.scss / forms.scss | Global styles, heavily used | Medium |
| 2 | Checkbox / Radio | `$color-positive`, hardcoded hex | Small |
| 3 | Card | `$light`, `$dark`, `$grey` + lighten/darken | Medium |
| 4 | Tabs | Mixed strategies in same file | Medium |
| 5 | DatePicker | Hardcoded colors, `$font-color-base` | Medium |
| 6 | Dropdown | `#9e9e9e` hardcoded, `$light` | Small |
| 7 | Select/Search | SCSS variables | Small |
| 8 | QueryBuilder | SCSS variables | Small |
| 9 | Stepper | `$light` references | Small |
| 10 | Remaining ~70 files | Varies | Long tail |

### What the Diff Looks Like per Component

A typical component migration PR:
- **1 file changed** (the `.scss` file)
- **~10-30 lines** modified (variable swaps)
- **No TypeScript changes** (purely CSS)
- **No template changes**
- **Visually identical** in light mode (same colors, just referenced differently)
- **Now responds to theme swap**

### Verification Strategy

For each migrated component:
1. Visual regression: screenshot in light mode before/after (should be identical)
2. Theme swap: toggle `data-theme="dark"` and confirm the component responds
3. Fallback: remove the theme CSS entirely — component should still render (using inherited styles or defaults)

## Implementation in novo (app)

### Changes Required

#### 1. Load theme CSS from tokens

**angular.json styles array:**
```json
"styles": [
  "node_modules/novo-design-tokens/css/themes.css",
  "node_modules/prismjs/themes/prism-okaidia.css",
  "apps/novo/styles/variables.scss",
  "apps/novo/styles.scss"
]
```

#### 2. Update theme toggle

**Before (Mainframe.app.ts):**
```typescript
toggleDarkMode() {
  document.documentElement.classList.toggle('theme-dark');
  // broadcast to child frames...
}
```

**After:**
```typescript
toggleDarkMode() {
  const current = document.documentElement.getAttribute('data-theme');
  const next = current === 'dark' ? 'light' : 'dark';
  document.documentElement.setAttribute('data-theme', next);
  // broadcast to child frames...
}
```

#### 3. Remove duplicate variable definitions

`apps/novo/styles/variables.scss` currently re-declares many color aliases. After novo-elements provides theme-responsive variables, these can be deleted.

## Rollout Strategy

### Timeline

| Phase | Work | Duration | Dependency |
|-------|------|----------|------------|
| A | Semantic tokens in novo-design-tokens | 1-2 days | None |
| B | Build system: generate themes.css | 1 day | Phase A |
| C1 | novo-elements infrastructure (theme files, directive, service) | 2-3 days | Phase B |
| C2 | Component migration (incremental, 5-10/week) | 3-5 weeks | Phase C1 |
| D | novo app integration | 1 day | Phase C1 |

**Phases A + B + C1 + D can ship in ~1 week.** They establish the infrastructure without changing any component visuals. After that, component migrations (C2) happen incrementally in the background.

### Backwards Compatibility

- Existing `css/variables.css` and `css/variables-dark.css` continue to be generated (unchanged)
- Existing SCSS variables continue to work (unchanged)
- Components that haven't migrated keep working (just aren't theme-responsive)
- The `var(--x, $fallback)` pattern means partial migration is safe
- `NovoTheme.use()` API doesn't change, just works better

### Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Semantic token names don't cover all component needs | Medium | Low | Iterate — add tokens as components surface gaps |
| Visual regression during component migration | Low | Medium | Screenshot testing before/after |
| Entity colors need dark variants | Medium | Medium | Start with static entity colors; add dark variants later if needed |
| Third-party/embedded content doesn't respect theme | Low | Low | Scoped — those stay as-is |
| Performance of 60+ CSS variables on :root | Very Low | Low | Browsers optimize this; well under threshold |

## Definition of Done

After full implementation:

1. Setting `data-theme="dark"` on `<html>` causes **all** novo-elements components to render in dark mode
2. Theme definitions live in **one place** (novo-design-tokens) — no hand-maintained theme files
3. Creating a new theme requires **no component code changes** — just new token values
4. Component authors have a **documented contract** of which CSS variables to use
5. Zero SCSS variables or hardcoded colors in component style outputs that represent theme-dependent values

## Open Questions for Review

1. **Entity colors in dark mode** — Should `--color-company` change in dark themes, or stay constant for brand recognition? (Recommendation: keep static, but provide `--color-company-on-dark` variants for contrast)

2. **Number of themes** — Are we targeting just light/dark, or should the architecture support branded themes (customer-specific colors)? The `data-theme` approach supports unlimited themes.

3. **Transition animations** — Should theme swaps animate? (e.g., `transition: background-color 0.2s` on body). If yes, which properties?

4. **Component-level theme overrides** — Should individual components be overridable without a full theme? (The ThemeDirective already supports this, but should it be encouraged or discouraged?)

5. **Token naming convention** — The semantic tokens introduce new names (`surface-primary`, `text-primary`, `interactive-base`). Should we prefix them to avoid collision with existing `--background-main`, `--text-main` vars? (Recommendation: yes, use `--novo-` prefix or keep new names distinct, then deprecate old ones)
